# 4.2. Проверка работоспособности информационной системы

Проверка работоспособности разработанной информационной системы выполнена по двухуровневой схеме (рис. 4.2): модульное тестирование отдельных компонентов (white-box) и интеграционная проверка на типовых сценариях использования (black-box). Дополнительно предусмотрена пользовательская оценка качества интерфейса и формулировок опросника. Такой подход позволяет одновременно подтвердить корректность внутренней логики рекомендательного контура и пригодность системы для решения прикладной задачи в условиях, близких к реальной эксплуатации.

## Модульное тестирование компонентов

Модульное тестирование направлено на проверку устойчивости и предсказуемости ключевых блоков: кодирования ответов опроса, предсказания технологического стека, формирования рекомендаций, справочного обогащения, анализа HTML при онлайн-режиме, загрузки конфигурации и сохранения прогресса пользователя. Тесты реализованы на базе стандартной библиотеки `unittest` и запускаются единой командой `python run_tests.py`; по завершении в консоль выводится сводная таблица по компонентам.

Всего выполнено **49 автоматических тестов** по **8 компонентам**. По результатам прогона от 29.05.2026 все тесты завершились успешно; суммарное время выполнения составило **0,69 с**. Детализация по компонентам и ключевым проверкам приведена в табл. 4.2.

Наиболее значимые проверки:
- **SurveyEncoder** — корректное преобразование пропущенных ответов в `unknown`, обработка словарей и списков, сохранение размерности one-hot вектора;
- **mlp_model** — для эталонного профиля лендинга модель возвращает метку `gatsby_netlify`, структура top-3 и убывание вероятностей;
- **ai_stub** — разворот вложенных ответов блоков, извлечение URL, формирование полного offline-отчёта (`label`, `stack`, `design`, `top3`);
- **site_analyzer** — определение Next.js и PHP по HTML-заглушкам, извлечение цветов, обработка сетевых ошибок без падения приложения;
- **AppState** — контроль полноты блока и сериализация сессии;
- **loader / storage** — загрузка `questions.json` и сохранение прогресса в UTF-8.

Сетевые вызовы в тестах `site_analyzer` изолированы через mock-объекты; обращения к реальным сайтам в модульном контуре не выполнялись.

## Интеграционная проверка по сценариям S1–S4

На втором уровне система рассматривалась как «чёрный ящик»: для четырёх типовых профилей проекта (табл. 4.3) заполнялся опросник, после чего фиксировались предсказанный стек, полнота отчёта и время формирования рекомендации в автономном режиме. Схема сценариев представлена на рис. 4.3.

Результаты прогона (табл. 4.4):
- **S1 (лендинг)** — `gatsby_netlify`, время **0,07 с**, полный отчёт (6 полей стека, 9 параметров дизайна);
- **S2 (интернет-магазин)** — `nextjs_nestjs_pg`, **0,06 с**, соответствует fullstack-контуру с backend и БД;
- **S3 (SaaS)** — `react_nestjs_pg`, **0,06 с**, масштабируемый web-стек; уверенность top-1 ниже, чем у S1 (0,29), что согласуется со сложностью класса;
- **S4 (корпоративный desktop)** — `dotnet_wpf`, **0,06 с**, нативный Windows-профиль.

Среднее время формирования offline-отчёта по сценариям — **0,06 с**, что подтверждает пригодность системы для интерактивного использования.

## Верификация на основе известных продуктов

Для обоснования релевантности рекомендаций выполнено сопоставление с эталонными продуктами (табл. 4.5). Отдельно проведена проверка по профилю **маркетплейса ozon.ru** с опорой на открытые сведения о технологической платформе **Ozon Techpoint** (поддерживаемые языки: Go 1.23, Java 17, Python 3.11, C# .NET 8, C++ 20).

Пошаговая инструкция заполнения всех восьми блоков опросника для этого профиля приведена в файле `docs/chapter4/ozon_survey_guide.md` (для воспроизведения в GUI и скриншота отчёта).

В опроснике зафиксированы признаки крупного интернет-магазина: тип `ecommerce`, аудитория в РФ и за рубежом, команда 6+ человек, бюджет от 1 млн руб., нагрузка 20k+ пользователей, критичные SEO и платежи, SSR и React, микросервисная архитектура, высокий RPS, международное облако, полнотекстовый поиск, сфера retail, URL-ориентир `https://www.ozon.ru`.

В автономном режиме система выдала метку **`nextjs_nestjs_pg`** (вероятность top-1 ≈ **0,49**, время **0,04 с**), полный отчёт: Frontend — Next.js (React), Backend — NestJS (Node.js), БД — PostgreSQL, блок платежей и аналитики. Альтернативы в top-3: `nextjs_django_pg`, `wordpress_php`.

Сопоставление с Ozon Techpoint показывает **частичное соответствие**: по архитектурному классу (масштабируемый e-commerce с backend и СУБД) рекомендация релевантна; по **языкам программирования** — расхождение, поскольку корпоративный контур Ozon опирается на Go и Java, а справочник системы для веб-магазинов преимущественно описывает стеки на Node.js/Python/PHP. Ближайший по языку вариант из top-3 — `nextjs_django_pg` (Python 3.x в backend-контуре). Данный результат иллюстрирует границу применимости ИС: она уверенно определяет **тип продукта и fullstack-контур**, но не воспроизводит уникальный корпоративный стек крупного маркетплейса без расширения обучающей выборки.

Отдельно проведена проверка по профилю **Visual Studio Code** — кроссплатформенного редактора кода на **Electron** (Chromium + Node.js), исходники которого написаны на **TypeScript** и **JavaScript**. Пошаговая инструкция для GUI — в файле `docs/chapter4/vscode_survey_guide.md`.

В опроснике зафиксированы признаки desktop-редактора: тип `editor`, ОС Windows/macOS/Linux, международная аудитория, работа с файловой системой, полный офлайн-режим, явный выбор **Electron**, сфера **IT / DevTools**, боковая навигация, обязательная тёмная тема, расширяемость (плагины), автономное приложение без собственного сервера, URL-ориентир `code.visualstudio.com`.

В автономном режиме система выдала метку **`electron_js`** (вероятность top-1 ≈ **0,49**, время **0,05 с**), полный отчёт: Frontend — Electron (HTML/CSS/JS), Backend — Node.js (main process), БД — SQLite/IndexedDB, дистрибуция через GitHub Releases. Альтернативы в top-3: `tauri_rust`, `dotnet_maui`.

Сопоставление с реальным стеком VS Code показывает **полное соответствие** по платформе (Electron, Chromium, Node.js) и **высокую релевантность** дизайн-блока: рекомендованы IDE-подобный интерфейс, sidebar + tabs, шрифты JetBrains Mono и Inter, палитра с акцентом `#007ACC`, подсветка синтаксиса и Git-интеграция — что совпадает с визуальным языком продукта. В отличие от профиля Ozon, здесь расхождение по языкам **отсутствует**: TypeScript/JS в VS Code укладываются в рекомендуемый Electron/Node.js контур.

### Проверка online-анализа веб-страницы

Для демонстрации модуля `site_analyzer` выбран **нишевый российский сайт** [productradar.ru](https://productradar.ru) — каталог IT-стартапов (не относится к числу наиболее цитируемых площадок вроде Ozon или Habr). Пошаговая инструкция — `docs/chapter4/productradar_survey_guide.md`.

В опроснике указан URL в полях **w4** и **w_d5**; тип сайта — лендинг/витрина, аудитория РФ, backend PHP, сфера tech, SSR, монолит, российское облако. На экране результатов активируется переключатель **«Режим с AI»** (требуется интернет).

Результат online-прогона (табл. 4.4, продолжение): анализ завершился **без ошибки** за ~**8 с**; парсер определил **PHP**, **Tailwind CSS**, **Яндекс.Метрику**, тип навигации (расширенное меню, 51 ссылка); KMeans построил **палитру из 5 цветов**. Offline-метка **`wordpress_php`** (p≈0,24, 0,04 с) согласуется с PHP-контуром, обнаруженным в HTML. Фреймворк frontend в разметке явно не маркирован — типичное ограничение эвристического парсера.

Также выполнено сопоставление с habr.com, vercel.com, linear.app, Telegram Desktop (табл. 4.5). Совпадение оценивалось как «Да», «Частично» или «Нет».

## Пользовательская оценка (UX)

Для проверки удобства системы опрос самостоятельно прошли **15 участников** с разным уровнем подготовки (студенты 2–4 курса и магистратуры, junior/middle/senior-разработчики, менеджер проекта, стажёр). После прохождения опроса и просмотра итогового отчёта каждый участник выставил оценки по **пятибалльной шкале** по трём критериям и оставил текстовый комментарий. Результаты сведены в **табл. 4.6**.

Средние баллы: понятность вопросов — **4,0**, полезность рекомендаций — **4,1**, удобство интерфейса — **4,3**. Наиболее частые замечания — недостаточность подсказок к терминам (SSR, microservices, CI/CD), необходимость явнее различать offline- и online-режим на экране результатов, пожелание добавить экспорт отчёта. В целом участники отметили быстроту offline-режима, логичную структуру блоков опроса и пригодность отчёта для предпроектного черновика.

## Вывод по § 4.2

Модульное тестирование подтвердило архитектурную целостность компонентов (**49/49** успешно). Интеграционные сценарии S1–S4 выполнены без сбоев; система формирует полный structured-отчёт за доли секунды. Выявленные ограничения (зависимость online-контура от сети, сниженная уверенность на сложных SaaS-профилях) носят ожидаемый характер и учтены в § 4.3.
